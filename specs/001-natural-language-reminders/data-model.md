# Data Model: Natural-Language Reminder Agent — Part 1B

This design models request/response data and evaluation evidence only. Reminder
records are supplied by the caller for each request; the prototype has no
persistent reminder store.

## Request Data

### ReminderRequest

| Field | Type | Required | Rules |
|---|---|---:|---|
| `request` | string | Yes | Non-empty natural-language request. |
| `reference_context` | object or omitted | No | When present, contains `current_datetime` and `timezone`. |
| `existing_reminders` | array or omitted | No | Omit or provide an empty array for create requests; supply relevant records for updates. |

`reference_context.current_datetime` is an ISO-8601 date-time with UTC offset.
`reference_context.timezone` is an IANA time-zone identifier or `null`.

### ExistingReminder

| Field | Type | Required | Rules |
|---|---|---:|---|
| `reminder_id` | string | Yes | Non-empty and unique within the supplied list. |
| `task` | string | Yes | Non-empty record task text; copied to update actions. |
| `date` | string | Yes | `YYYY-MM-DD`; current record date. |
| `time` | string | Yes | 24-hour `HH:MM`; current record time. |
| `timezone` | string or null | Yes | IANA identifier when known; otherwise null. |

The request must contain an identifying description or explicit ID that matches
exactly one supplied record. A single record in context does not by itself
identify the target. Missing, invalid, duplicate, or ambiguous IDs require
clarification. An update action's `target_reminder_id` is copied exactly from the
matched record. No ID is generated by the agent.

## ReminderResponse

The response is a strict, status-discriminated JSON object. The complete JSON
Schemas are in [`contracts/reminder-response.schema.json`](./contracts/reminder-response.schema.json).

| Status / kind | Required action fields | Target ID rule |
|---|---|---|
| `action` / `create` | `kind`, `task`, `date`, `time`, `timezone` | `target_reminder_id` is prohibited. |
| `action` / `reschedule` | `kind`, `target_reminder_id`, `task`, resulting `date`, `time`, `timezone` | ID must match exactly one supplied record; task is copied from that record. |
| `action` / `snooze` | `kind`, `target_reminder_id`, `task`, resulting `date`, `time`, `timezone` | ID must match exactly one supplied record; task is copied from that record. |
| `clarification` | `status`, `action: null`, one or more focused `questions` | No target ID or action payload. |
| `rejected` | `status`, `action: null`, non-empty `reason` | No target ID or action payload. |

The date and time are the resulting local calendar date and wall-clock time in
`YYYY-MM-DD` and `HH:MM` form. For create, the time zone comes from the request or
is null. For updates, use the requested time zone if supplied; otherwise use the
matched record's time zone or null. Missing schedule components may be copied from
the matched record only when the request clearly means to leave them unchanged;
otherwise clarify.

## EvaluationCase

The future `evaluation_cases.jsonl` file uses one JSON object per line, with each
line representing one independent evaluation case; this plan does not create that
dataset. Every line is parsed and validated independently against the case schema.
An invalid line is reported with its line number and case ID when available; it
must not be silently skipped or treated as a valid case. The case contains:

- Stable `case_id` and one required category: normal, boundary, ambiguous,
  missing information, malformed, or adversarial.
- The complete `ReminderRequest`, including input context needed to interpret
  relative dates or identify update targets.
- Expected outcome, intended action kind, semantic task meaning, exact expected
  target ID where applicable, expected date/time/time zone or explicit unknowns,
  clarification topic or rejection reason, and a critical-safety indicator.
- A semantic reference note describing equivalent meanings that should score
  correctly without exact string equality.

The case format is documented in
[`contracts/evaluation-case.schema.json`](./contracts/evaluation-case.schema.json).
The maintained dataset must cover all 20 cases enumerated in the feature spec.

## SemanticAssessment and EvaluationResult

For each case, `SemanticAssessment` records a 0-2 integer score and non-empty
reason for each of: intent, task/target identification, schedule interpretation,
clarification/rejection correctness, and unsupported assumptions. The sum is
0-10. It also records `evaluator_method`, distinguishing rubric-based assessment
from an optional LLM judge. The method is independent of the live
reminder-interpretation provider; a second live LLM is not required. The
assessment format is in
[`contracts/semantic-assessment.schema.json`](./contracts/semantic-assessment.schema.json).

`EvaluationResult` keeps the input case ID, actual response, deterministic
structural results, behavioral property results, the five semantic scores and
reasons, semantic evaluator method, weighted component and aggregate scores,
pass/fail, interpretation-provider configuration, optional evaluator/model
configuration, and any critical-failure flags. Initial results are retained
separately from post-repair results.

## HumanDecision and Run Lifecycle

An evaluation run records its dataset and check configuration, initial or
post-repair phase, results, and one explicit human decision (`ACCEPT` or `REJECT`)
after final results are presented. Automated pass/fail is not a human decision.

Request processing is a pure proposal flow:

1. Validate request and supplied context.
2. Interpret the request and produce an action, clarification, or rejection.
3. Validate response shape and behavioral properties before exposing an action.
4. Return the JSON response; do not update a reminder store or trigger scheduling.
